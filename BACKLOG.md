Task backlog for the site. Grouped by horizon — **Now** (do soon / quick wins), **Next** (on deck), **Later** (deferred or needs a decision first). Checkboxes are standard GitHub task syntax (`- [ ]` open, `- [x]` done). Size tags: `[S]` quick, `[M]` moderate, `[L]` substantial.

## Now

- [ ] **Disable GitHub Pages build/deploy** `[S]` — The repo's "pages build and deployment" GitHub Actions workflow runs and **fails** (it can't build this Hugo-on-Netlify source), and emails failure notices. GitHub Pages is unused (Netlify is the sole deploy target). Turn it off: repo **Settings → Pages → Source: None**.
- [ ] **Fix terminal/CLI `git push`** `[M]` — Pushes currently only work via the **Tower** GUI client. The remote is HTTPS (`https://stefanherzog@github.com/stefanherzog/blogdown.git`) with no stored credential, and the embedded/Zed shell is non-interactive so git can't prompt (`could not read Password … Device not configured`). SSH also fails — `ssh -T git@github.com` → `Permission denied (publickey)`, i.e. the local `~/.ssh/id_ed25519` key isn't registered with GitHub (or not loaded in the agent). Fix: (a) add the SSH public key to GitHub and `git remote set-url origin git@github.com:stefanherzog/blogdown.git`; or (b) configure an HTTPS credential — store a PAT in the `osxkeychain` helper (already configured), or install `gh` then `gh auth login` + `gh auth setup-git`.
- [ ] **Disable Netlify "Legacy Prerendering"** `[S]` — Enabled but deprecated by Netlify. Harmless to remove for a static Hugo site (prerendering only matters for client-rendered JS apps). Netlify dashboard → it prompts to disable via *Configure*.
- [ ] **Bump Netlify build Node.js 16.x → 24.x LTS** `[S]` — Node 16 is end-of-life. The Hugo build almost certainly doesn't use Node (SCSS compiles via Hugo's built-in extended libsass, no PostCSS/npm), so this is low-risk housekeeping. Prefer pinning **in-repo** for reproducibility: add `NODE_VERSION` under `[build.environment]` in `netlify.toml` (next to `HUGO_VERSION`) or a `.nvmrc`, rather than only the dashboard.

## Later

- [ ] **Strategic website goals review** `[M]` — Step back and decide what this site should do before activating more sections. Key questions: What audiences does it serve (researchers, journalists, collaborators, students, public)? What content types are worth maintaining long-term (writing, talks, projects, data)? How do Bluesky and LinkedIn fit: do they replace certain site sections (short-form commentary), complement them (driving traffic to longer pieces), or should the site aggregate/link to them? What does success look like in 2 years? This review should feed the "decide which demo sections go live" and "framework evaluation" tasks — don't proceed with those until goals are clearer.
- [ ] **Programmatic CV: single source → HTML + PDF** `[L]` — Replace the current macOS Pages → manual PDF export workflow with a data-driven CV. Goal: one canonical source (e.g. YAML, JSON Resume, or an R Markdown/Quarto document) that generates both a styled PDF and an HTML page, identical by construction. The `stefanherzog.org/cv` URL must always resolve (already linked in external places) — either keep it pointing at a PDF iframe or make it a proper HTML page. Candidates: `vitae` R package (Quarto/R Markdown → PDF + can render HTML), JSON Resume spec + a Hugo data template for HTML + a headless-browser PDF export, or Pandoc-driven approach. Also consider whether the HTML CV replaces or supplements the PDF embed. Decide after the strategic goals review.
- [ ] **Publications list from Zotero** `[L]` — Add a publications section to the site, sourced from Zotero. Candidate pipeline: Zotero → Better BibTeX plugin → auto-export CSL-JSON → Hugo reads as a data file → rendered by a list layout (grouped by year or type). Alternatively, keep Zotero as the authoritative store and generate a static `.bib` or `.json` snapshot committed to the repo (simpler, no live sync). Decide: should publications be a standalone page, integrated into a "research" section, or part of an HTML CV? Assess overlap with the programmatic CV task — they may share the same data source.
- [ ] **Evaluate alternative frameworks** `[L]` — Once strategic goals are clearer, assess whether hugo-apero is the right foundation long-term. Known pain points: old Hugo pin (0.101.0), theme is vendored + unmaintained, no built-in academic features (publications, talks schema). Candidates worth evaluating: **Hugo Academic / Wowchemy** (purpose-built for researchers, but complex), **Quarto website** (familiar R toolchain, good for CV + publications, less flashy), **Astro** (modern static site generator, very flexible, good performance), staying with hugo-apero after a Hugo version upgrade. Criteria: ease of CV + publications integration, Zotero pipeline support, maintenance burden, design flexibility. Block on strategic goals review.

It's the thumbnail shown when the site is shared (Bluesky/LinkedIn/Twitter). Consider a photo of Stefan or a research-themed image: drop it in `static/img/` and update `sharing_image`. Discretionary.
